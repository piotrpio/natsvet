## Context

`streamconfig` walks every composite literal with the inspector, keeps those of `jetstream.StreamConfig`/`nats.StreamConfig`, wraps their fields in `natsapi.Fields` (constant-only view, masked by `Masker`) and runs a list of top-level checks. Nested literals are only presence-tested (`Fields.Ptr`, `Fields.SliceLen`). `kvconfig` does the same for KeyValue/ObjectStore configs with client-side checks only. See proposal.md for motivation.

Source this design was derived from, to be re-derived line by line at implementation time:

- nats-server v2.14.7 (`8d8b69a`, the corpus pin; identical in these functions to `main` at `7cbac9c`): `checkStreamCfg` in `server/stream.go` — the `Mirror` block (consumer checks, `FilterSubject` + `SubjectTransforms`, per-transform `IsValidSubject` then `ValidateMapping`, pairwise `SubjectsCollide`, `isValidAssetName(Mirror.Name)` only when `External == nil`); the `Sources` loop (`src == nil || !isValidAssetName(src.Name)`, `composeIName` duplicates (not ported, see proposal Non-goals), `FilterSubject` + `SubjectTransforms`, per-transform validity and `ValidateMapping`, pairwise `subjectIsSubsetMatch`, consumer checks, `composeCName` duplicates (not ported)); the default subject (`Subjects = [Name]` when `Subjects`, `Mirror` and `Sources` are empty — before the republish check); the stream `SubjectTransform` (validity then `ValidateMapping`); `RePublish` (empty source → `>`, pedantic-only errors, the implicit `>`→`>` substitution when `SubjectTransform != nil && len(Subjects) == 1 && SubjectTransform.Source == Subjects[0]`, the `SubjectsCollide(dest, subj)` cycle, then `NewSubjectTransform(src, dest)`). `ValidateMapping` in `server/sublist.go` (token scan: empty token or token after `>`, `{{…}}` tokens matching none of the ten function expressions, whitespace in a plain token; then `NewSubjectTransform`). `NewSubjectTransformWithStrict(src, dest, false)` and `indexPlaceHolders` in `server/subject_transform.go` (empty dest → valid; empty src → `>`; `subjectInfo` validity, no `*` in dest, `>` in both or neither; per-token placeholder parsing; wildcard index `> npwcs`; functions other than `Partition`/`Random` with a literal source). Error texts from `server/errors.go` (`mappingDestinationErr` formats as `<err> in <token>`).
- nats.go v1.53.1 (the `testdata` pin): no client-side transform or republish validation; `convertStreamConfigDomains` / `convertDomain` in `jetstream/jetstream.go` and `jsm.go` fail with `nats: domain and external are both set` on `CreateStream`, `UpdateStream`, legacy `AddStream`/`UpdateStream`, and `CreateKeyValue` (which calls `CreateStream`); `prepareKeyValueConfig` in `jetstream/kv.go` and legacy `CreateKeyValue` in `kv.go` pass `RePublish` through, copy `Mirror` and prefix its name with `KV_`, ignore `Sources` when `Mirror` is set, prefix source names, and set `Subjects = ["$KV.<bucket>.>"]` unless mirrored. They differ on source transforms: `jetstream` passes a source that has `SubjectTransforms` through unchanged and adds a `$KV.<src>.>` → `$KV.<bucket>.>` transform only to sources that have none; legacy `CreateKeyValue` (`kv.go` ≈510) assigns that transform whenever `External == nil` or the source is another bucket, overwriting whatever the literal set. `StreamSource.Consumer` (`StreamConsumerSource{Name, DeliverSubject}`) exists only in `jetstream`.

Corpus baseline (grep over the pinned clones): explicit `SubjectTransformConfig{` literals — nats-server 18, nats.go 19, orbit.go 6, nack 3; `RePublish{` — nats.go 8, nats-server 3, nack 2, natscli 2; `StreamSource{` — nats-server 169, nats.go 31, nack 4, orbit.go 4, natscli 3, eventing-natss 1 (elided-type slice elements not counted). nats-server's `server/jetstream_test.go` builds the invalid cases with nats.go types (≈9645–9663 mirror filters, ≈18059–18127 bad transform sources and destinations on stream/source/mirror, ≈23082/23104 republish cycles, ≈23681/23709 source filters), so `FP` lines of the "test asserts the rejection" kind are expected; nats.go's corpus scope (`./examples/... ./test/...`) excludes `jetstream/test/`.

## Goals / Non-Goals

**Goals:**
- Every check is the server's (or nats.go's) own, on constants, reported at the nested literal it is about, in the server's words.
- A nested literal is checked wherever it is written; context is used only for the checks that cannot be true without it, and to skip the checks nats.go makes untrue by rewriting the literal (legacy KeyValue sources).
- The transform parser is a port pinned by the server's tables, not a reading of the grammar.

**Non-Goals:**
- Following a nested value through variables to its parent (`cfg.Mirror = m` with `m` built elsewhere). The literal of `m` gets its context-free checks where it is written; parent checks need the literal in place.
- First-error-only reporting. The server stops at the first rejection; the rule reports every independent finding in a literal, as the existing top-level checks do.

## Decisions

**Extend `streamconfig`, no new rule.** The checks live in the same server function as the top-level ones, the messages read `stream config: …`, and users disable them together. `kvconfig` gets only the bucket-subject cycle, because the subject it collides with is KeyValue knowledge (`$KV.<bucket>.>`) the stream rule does not have. Alternative: a `transform` rule for everything mapping-shaped — rejected; it would split one server function across two rule ids and need a second Doc for the same failure (`CreateStream` rejects the config).

**Two visit points in one pass.** The inspector already visits every `CompositeLit` once. `streamconfig` now matches, besides the stream config types, `SubjectTransformConfig`, `RePublish` and `StreamSource` (both packages) and runs the context-free checks on each at its own visit (proposal: "Checks on the nested literal alone"). Parent checks run when the stream config literal is visited: they read the nested literals through `Fields.Lits` and report at those literals' positions. No check runs at both points, so nothing is reported twice. `StreamConsumerSource` is not matched on its own; its fields are read from its parent `StreamSource` literal, because every consumer check needs the source's `OptStartSeq`/`FilterSubject` too.

**Mirror role from the stack, not from the parent visit.** The stricter mirror overlap test (`SubjectsCollide`) applies to a `StreamSource` literal written as `Mirror:` of a stream config or a KeyValue config literal (nats.go copies a KeyValue mirror into the stream's mirror unchanged but for the name). At the `StreamSource` visit the stack gives the enclosing `KeyValueExpr` (through an optional `&`) and the literal above it; `CompositeFields` on that literal with the stream and KeyValue config refs answers "is this a mirror". Doing it at the parent visit instead would need `kvconfig` to run a stream-transform check — rejected. A mirror literal bound to a variable gets the looser subset test only.

**Parent checks exclude KeyValue parents on purpose.** Source and mirror name validity and the stream republish cycle run only under a stream config literal: nats.go rewrites KeyValue source names (`KV_` prefix, so `Name: ""` becomes a valid `KV_`) and uses `$KV.<bucket>.>` as the subject set. A model of `prepareKeyValueConfig` would be needed for either; the one KeyValue parent check with a clear rule — the republish cycle — is `kvconfig`'s.

**Legacy KeyValue sources skip the transform checks.** Legacy `CreateKeyValue` overwrites a source's `SubjectTransforms` unless it is an `External` source of the same bucket, so for a `StreamSource` element of a `nats.KeyValueConfig` literal's `Sources` the transform-source, mapping, filter-and-transforms and overlap checks — on the source and on the `SubjectTransformConfig` literals inside it — would describe transforms the server never receives. At the nested visit the rule walks up the inspector stack; if it passes through the `Sources` key of a composite literal of type `nats.KeyValueConfig` before reaching the root, those checks are skipped. The `Domain`/`External` check still runs (legacy `AddStream` calls `convertDomain`), and nothing changes for `jetstream.KeyValueConfig`, which submits a source's own transforms as written. Modelling the exception precisely (skip only when the overwrite happens) was rejected: the `External`-and-same-bucket case needs the bucket and source names as constants, is rare, and the looser skip cannot report anything untrue. Alternative: drop the transform checks on every legacy `nats.StreamSource` — rejected with the maintainer; legacy stream sources are most of the corpus's usage (nats-server tests), and only the KeyValue path rewrites them.

**`ValidateMapping` port in `natsapi/transform.go`.** Ported: the ten function expressions verbatim (unanchored `FindStringSubmatch`, greedy `(.*)` — the server's `{{wildcard(1)}}{{split(3,1)}}` error depends on it), the comma splitter, `indexPlaceHolders` returning only the transform type, wildcard indexes and error, `transformIndexIntArgsHelper`, `subjectInfo`, the non-strict error paths of `NewSubjectTransformWithStrict`, and `ValidateMapping`. Not ported: the transform runtime (`Match`, `TransformTokenizedSubject`, partition hashing) and strict mode. Errors are `mappingDestinationErr`-shaped values whose `Error()` is the server's text, so diagnostics can quote it and the tests compare strings. Exported as `ValidateMapping(src, dest string) error` and `SubjectTransformErr(src, dest string) error`. Tests: `TestValidateDestinationSubject` and the non-strict `shouldErr`/`shouldBeOK` rows of `TestSubjectTransforms` (the strict-accepted `bar.{{Wildcard(1)}}` row is also non-strict-accepted and is kept), plus error-text rows for the spec scenarios. Promoted to `natsapi` rather than kept in `analyzers/streamconfig`: it is server-semantics code pinned by server tables, exactly like `subject.go`, and a nats-server bump re-verifies both in one place. Alternative: import the server package — rejected; the only production dependency is `golang.org/x/tools`.

**`Fields.Lits(field) ([]*ast.CompositeLit, bool)`.** Returns the literal of a struct or pointer field (`T{…}`, `&T{…}`, through parentheses) or the element literals of a slice literal (elided `{…}` and `&T{…}` elements), with `complete` false when any value is not a literal or the field is masked or absent-but-masked. The parent checks call `CompositeFields` + `NewFields` on each returned literal with the parent's masked set (the `Masker` climbs through enclosing literals to the root binding, so the set is the same one a nested visit would compute). `nil` elements of `Sources` (the server rejects `src == nil`) are found by walking the raw slice literal from `Fields.Expr`; `Lits` reports them as incomplete. Alternative: re-run `Masker.Masked` per nested literal from the parent visit — rejected; the parent has no stack for its children, and the answer is identical.

**Indexed assignments mask the field.** `AssignedFields` recorded only a `SelectorExpr` left-hand side, so `cfg.Sources[0] = src` and `cfg.Subjects[1] = "b"` changed a checked field without masking it — a latent false positive in the existing `Subjects` checks too. It now unwraps `IndexExpr` chains down to a `SelectorExpr` and records its name. This can only remove findings. The corpus diff shows whether any existing line goes away; if one does, it was a false positive.

**Role-neutral messages, server detail verbatim.** The server words the same rejection per role (`stream transform source: …`, `source transform: …`, `mirror transform: …`); a `SubjectTransformConfig` literal does not always know its role, so messages say `subject transform …` and append the server's error text unchanged (`invalid mapping destination: wildcard index out of range in {{split(3,1)}}: [3]`). The consumer message adds a reason the server omits (it reports only `stream source consumer config is invalid`), because four different fields lead to it. The cycle message names the colliding subject, which the server does not.

**Durable-source consumer checks ship default-on.** The field is documented as requiring nats-server 2.14; an older server ignores it and sources without a durable consumer. Anyone who sets it targets 2.14+, where the checks are exactly the server's; on an older server the configuration is still wrong for what it asks. Alternative: skip them until corpus evidence exists — rejected; they are deterministic server rejections like every Tier 1 check, and the server's own tests (`jetstream_test.go` ≈24080) show the empty-name and empty-deliver-subject shapes.

**The implicit republish is modeled, the pedantic errors are not.** A `RePublish{Source: ">", Destination: ">"}` with a matching single-subject `SubjectTransform` is accepted by the server and republishes on the transform destination; reporting it as a cycle would be false. It is resolved exactly as the server does, and when a transform field or the single subject is not constant the rule is silent. The pedantic-mode rejections are not reported: nats.go never sends `pedantic`.

## Risks / Trade-offs

- [The port drifts from a future nats-server] → The tables pin today's behavior; `docs/design.md` §3's re-derivation rule applies on a server bump, and `transform.go` names nothing but the server functions it mirrors, so a diff of those two server files is the whole review.
- [Name-based masking over-masks nested fields: `cfg.Name = x` also masks every nested `Name`] → Accepted; it can only silence checks, never add a false one, which is the direction the project prefers.
- [Several findings on one literal where the server reports one] → Consistent with the existing top-level checks; each finding is independently true.
- [A stream source built in a helper and appended (`cfg.Sources = append(cfg.Sources, mk("A"))`) escapes the parent checks] → Accepted; the literal inside `mk` still gets its context-free checks.
- [A standalone `nats.StreamSource` literal with transforms that is later appended to a legacy `nats.KeyValueConfig`'s `Sources` gets transform findings the server never sees] → Accepted and recorded: it needs the legacy API, KeyValue sourcing and hand-written transforms together, and the literal is invisible as a KeyValue source where it is written.
- [nats-server test files add many `FP` lines to `corpus.expected`] → Expected and labeled "test asserts the rejection", like the 30 `config-rules` lines; the triage task names the ranges.

## Migration Plan

None. Existing diagnostics are unchanged; new ones appear on upgrade. The `kvconfig` Doc string and the `rule-kvconfig` purpose paragraph are rewritten to cover one server-side check (the delta format carries requirements only, so the purpose edit happens in the main spec at archive time).
