## Context

`legacyjs` (opt-in) reports every identifier whose object is in the generated legacy table (`internal/natsapi/legacy_table.go`, 324 symbols from nats.go v1.53.1: `JetStreamManager` 22, the `KeyValue` family about 60, the `ObjectStore` family about 50, `JetStream` publish and subscribe, message methods, options, config types, enums, errors). The corpus counts it on every run: nats-server 8421 (tests), nats.go 2568 (tests), eventing-natss 227, go-choria 207, natscli 30, nack 6, orbit.go `natssysclient` 5. nats.go ships a human guide, `jetstream/MIGRATION.md` (749 lines, with KeyValue and object store sections and a subscribe-option-to-`ConsumerConfig` table). See proposal.md for motivation; an earlier draft design note was reviewed against the source, corrected, grilled with the maintainer and folded in here.

Facts this design rests on, checked in nats.go v1.53.1 and nats-server v2.14.7, to be re-derived in task 1.1:

- `jetstream` wraps a context without a deadline in `DefaultTimeout` (`jetstream.go` `wrapContextWithoutDeadline`; `defaultAPITimeout` = 5s); the legacy default wait is `defaultRequestWait` = 5s (`js.go`). `nats.MaxWait` is a `time.Duration` type usable as a handle option; `jetstream.WithDefaultTimeout` is its handle-level twin.
- `StreamManager` has `CreateStream`, `UpdateStream`, `CreateOrUpdateStream`, `Stream`, `StreamNameBySubject`, `DeleteStream`, `ListStreams`, `StreamNames` — no purge, info or message calls; `js.Stream(ctx, name)` sends `STREAM.INFO` (`jetstream.go`). `StreamConsumerManager` has create, update, create-or-update, get and delete for pull and push consumers, plus ordered, pause, resume and reset. `PushConsumer` has `Consume`, `Info`, `CachedInfo` only.
- Legacy `AddConsumer` (`jsm.go`) looks the consumer up by name first: identical config returns it, a different config fails with `ErrConsumerNameAlreadyInUse`; that is `jetstream.CreateConsumer`'s create action, not create-or-update.
- Legacy subscribe resolves an unbound subscription's stream with `js.StreamNameBySubject(subj)` (`js.go`), the same stream-names request `jetstream.StreamNameBySubject` sends; sets `FilterSubject` to the subject; wraps callbacks as `ocb(m); m.Ack()` unless `ManualAck`, `AckNone` or ordered; sets `MaxAckPending` to the channel capacity for channel subscriptions without one; and marks consumers it created for deletion on `Unsubscribe`/`Drain` (`jsi.dc`, push and pull alike). The server treats a consumer as durable only when `Durable` is set (`consumer.go` `isDurable`) and gives every other consumer an inactive threshold, 5s by default (`updateInactiveThreshold`).
- `jetstream` `Fetch` drops timeout and no-message statuses without setting the batch error (`pull.go`): an empty batch has `Error() == nil`; `Consumer.Next` returns `nats.ErrTimeout`.
- Legacy KeyValue methods such as `Get(key string)` take no options; `Watch` takes `WatchOpt`, which includes `nats.Context`.

## Goals / Non-Goals

**Goals:**
- A plan an agent can execute without recalling the API mapping, and a human can review: exact text where the answer is known, the question where it is not, and defaults that change nothing but what the migration is for.
- Every intermediate step compiles; proven by a test that applies the plan step by step, on the testdata module and on natscli.
- A plan format a later `natsvet migrate apply` can execute unchanged.
- One source for the mapping, checked against the pinned nats.go and its `MIGRATION.md`, so the plan and the upstream guide cannot drift apart.

**Non-Goals:**
- Executing the plan outside tests (see proposal Non-goals). The test-only applier is deliberately not exposed as a command.
- Deciding style questions the legacy code does not pose (naming beyond the temporary `New` suffix, package layout, logging).

## Decisions

**A subcommand in the natsvet binary, not an analyzer and not a second binary.** `cmd/natsvet` checks `os.Args[1] == "migrate"` before `multichecker.Main`, as it does for `-version`, and calls `migrate.Main(os.Args[2:])` with its own `flag.FlagSet`; `migrate plan` and `migrate skill` are its actions. The go vet and go fix protocols never pass `migrate` first, so no existing mode changes (analyzer-framework spec). Alternative: grow `legacyjs` into the report — rejected: analyzers run per package and emit diagnostics, components cross packages, and the only cross-package channel, Facts, flows one way, which is what forced the earlier draft's "package-local only" limit. Alternative: a `natsvet-migrate` binary — rejected: a second install and a second version to keep in step with the analyzers that verify its output.

**Whole-program load with `go/packages`.** One `packages.Load` with `NeedName|NeedFiles|NeedSyntax|NeedTypes|NeedTypesInfo|NeedImports|NeedDeps|NeedModule` and `Tests: true` type-checks the named packages together, so a struct field or function declared in one package is the same `types.Object` in every package that uses it. Components are then a union-find over `types.Object`s — no Facts, no package-local restriction. Test variants of a package are merged by position so a site is never listed twice. The module's nats.go requirement comes from `packages.Module` of the loaded packages.

**Four site classes.** mechanical (exact text), guided (template plus facts; the text depends on surrounding code, e.g. a `Fetch` loop's body and error handling), decision (pattern, options, default, reason), unmapped (reason). Guided exists because pretending those sites are mechanical would mean either rewriting code the planner does not own or emitting text that does not compile; pretending they are decisions would ask questions that have one right answer. An answered decision turns its site into mechanical or guided.

**Defaults preserve behavior; pull is the one exception.** A migration whose defaults change behavior makes the user audit every default, which defeats having defaults. So `ack` defaults to acking after the handler returns (the legacy wrapper, reproduced as a wrapper at the `Consume` call), `channel-max-ack-pending` to keeping `cap(ch)`, `shared-handler` to a split that keeps both behaviors. `subscribe-target` defaults to pull because moving to pull consumers is why teams migrate, and the question is asked explicitly anyway — except for a subscription bound with `nats.Bind`, whose consumer already exists on the server as a push consumer (legacy binds nothing else, `processConsInfo`), so pull would fail at runtime and the default is `js.PushConsumer`. Consumers that legacy subscribe would create are created with `CreateOrUpdateConsumer`, as `MIGRATION.md` does; neither new call reproduces legacy exactly (legacy reused a compatible existing durable as it was, `CreateConsumer` compares the full configuration including server defaults, `CreateOrUpdateConsumer` applies the code's configuration), so the site carries a note naming the difference. `push-only-option` exists only after pull is chosen, where no equivalent exists. Two earlier decision patterns were removed because their behavior-preserving answer needs no question: an unbound subscription's stream is resolved with `StreamNameBySubject`, the very call legacy made, with the static name offered as a follow-up; and consumer teardown needs no step at all — explicit durables are kept (a note records that legacy `Unsubscribe` deleted durables it created), and every other consumer is removed by the server's inactive threshold. The planner never proposes `DeleteConsumer`.

**Follow-ups are not steps.** Changes that improve the result but are not needed to finish (a static stream name instead of the runtime lookup) are listed after the steps. For the stream name, the planner scans the loaded code for stream config literals (legacy and `jetstream`) with constant `Subjects`; exactly one covering the subscription subject makes a named candidate with its position, zero or several make an unnamed follow-up.

**The mapping table is Go data in `internal/migrate`.** One entry per legacy symbol: kind, target (package-qualified), shape (context position, pointer-to-value, option-to-field with the field name, stream-handle acquisition, rename), decision patterns it raises, a reason for unmapped entries, and the `MIGRATION.md` section anchor. Hand-written, because the mapping is judgment; checked by tests three ways (spec requirement): every key of the generated legacy table is present; every target resolves in the pinned `jetstream` package (loaded from the testdata module with `go/packages`, as `internal/tablegen` does); and every legacy-to-new row that `MIGRATION.md`'s mapping tables contain (read from the pinned module directory) agrees. The table records the nats.go version it was verified against. Alternative: generate the table from `MIGRATION.md` — rejected: prose tables are not complete (no `MaxWait` row, for example) and not machine-shaped; agreement is checked instead.

**Step 0 raises nats.go.** When the module requires a nats.go older than the table's version, the first step is `go get github.com/nats-io/nats.go@latest`. Within v1, later releases only add exported API, so every target the table verified exists afterwards, and `@latest` cannot cross a major version (v2 would be a different module path). Alternative: per-target minimum versions — rejected: a second table to verify against every intermediate release, for users who should upgrade anyway.

**Edits are machine-applicable from day one.** Each replacement is stored twice: `before`/`after` text for people and agents, and a list of edits `{file, start, end, new_text}` in byte offsets. A step's offsets are against each file as it stands after all earlier steps, and the step records the SHA-256 each file it touches must have before it runs; the plan also records every file's original hash. An applier therefore applies steps strictly in order, checks one hash per file per step, and applies a step's edits from the highest offset down — no offset shifting, and a file edited by hand in between is refused. The planner computes this by applying the steps to an in-memory copy of each file, tracking the identifiers it inserts (the `<name>New` handles) so the final rename step can address text that did not exist in the original file. Alternatives: offsets against the original file with the applier shifting them — rejected once implementation showed the rename step must edit inserted text, which has no original offsets; text only now, offsets with `apply` — rejected with the maintainer: it would change schema v1 and the skill's contract at the moment `apply` arrives.

**Replacement text splices original source.** A replacement is built from a template for the target call and the original source text of each argument (`fset` offsets), so comments and formatting inside arguments survive and no expression is re-printed. Tests parse every emitted replacement with `go/parser`, and the test applier type-checks it in place. Alternative: construct ASTs and print them — rejected: `go/printer` loses comments attached to the replaced nodes and reflows arguments.

**The context rule is a site property, computed once.** At each site the planner looks up the innermost scope for a `context.Context` variable (`types.Scope.LookupParent` from the site position), then for a `nats.Context(x)` among the call's options, then falls back to `context.Background()`. The fallback preserves the legacy 5s timeout, which is what makes most management, publish, KeyValue and object store sites mechanical rather than decisions.

**Dual-handle order with a fixed `New` suffix.** A component's steps: (1) at each root `nc.JetStream(opts...)`, add `<name>New, err := jetstream.New(nc, mapped opts...)` with the same error handling as the root; KeyValue and object store roots get `<name>New, err := <jsNew>.KeyValue(ctx, bucket)` and so on; (2) for every variable, struct field and parameter in the component, add a sibling of the new type named `<name>New` and assign it wherever the legacy one is assigned; (3) sites, mechanical first, then guided, then decided; (4) delete the legacy declarations and roots once no site uses them; (5) rename each `<name>New` to `<name>` (listed as a step; a gopls rename). The fixed suffix makes step 3's replacement text exact. A package-local component with no pending decisions is marked safe to apply in one commit; its steps do not change. Alternative: migrate each component atomically — rejected: legacy-heavy services form one component per service (the handle lives on a struct), and an atomic rewrite is one enormous diff that compiles only at the end.

**Components.** Roots are calls whose result type is a legacy handle (`nats.JetStreamContext`, `nats.JetStream`, `nats.JetStreamManager`, `nats.KeyValue`, `nats.ObjectStore` and their manager interfaces). Edges join two objects when a value flows between them: assignment and definition, call argument to parameter (including method receivers of user types that hold the handle), return value to result, struct field store and load, composite literal field. Objects of core types (`*nats.Conn`, `*nats.Msg` outside handlers) are not followed. A flow into a package outside the loaded set, or into test code while `-tests=false`, marks the component blocked there and drops its removal and rename steps.

**Tests are part of the program; components can be skipped.** Tests are loaded by default because a test that reads a struct field holding the handle belongs to that component, and removing the legacy field would break it. Code that must stay on the legacy API — tests of the legacy API itself, compatibility shims in libraries — is handled by the `component` pattern: `skip` keeps its sites out of the steps, counts them separately so progress can still reach zero, and blocks removal only of declarations it shares with a migrated component.

**Decisions by pattern and scope, recorded in the repository.** A pattern is a kind (`subscribe-target`, `ack`, `push-only-option`, `channel-max-ack-pending`, `shared-handler`, `component`) with a fixed option set; the plan groups pending sites by pattern at module scope. Answers live in `natsvet-migrate.json` at the module root — `{"version": 1, "answers": [{"pattern": "subscribe-target", "scope": "module", "choice": "pull"}]}` — read automatically, overridable with `-decisions`, committed with the first step that relies on them, and edited by hand or by the agent; `plan` never writes it. Scopes are `module`, `component:<id>`, `site:<id>`; the narrowest match wins. Site and component ids are derived from positions (file relative to the module root, line, column) of the site and of the component's first root, so they are stable across runs of an unchanged tree; after edits, `plan` reports answers whose scope no longer exists instead of dropping them. Alternative: a user-level cache — rejected: answers would not survive a new session, machine or teammate. Alternative: a `migrate answer` command that writes the file — deferred to the `apply` change, so this change keeps a single, read-only command.

**Plan schema and rendering.** JSON with `schema_version: 1`, sorted by file, line and column; `encoding/json` with `SetIndent` and no maps in the output model, so the output is byte-stable. Markdown through `text/template` from the same model: summary, pending decisions as questions with defaults, components and their steps, follow-ups.

**The skill is embedded.** `internal/migrate/SKILL.md` is the source (`//go:embed` cannot reach outside the package directory, so the skill lives next to the code that embeds it); `natsvet migrate skill` prints it. Every plan's header tells the agent to read it from the binary, so the skill always matches the schema the binary emits; a test checks that the version the skill names equals the plan's. Alternative: link to the repository file — rejected: version skew and a network dependency. Alternative: an `-install` flag writing into an agent harness directory — left out: harness layouts differ, and printing works with all of them.

**Verification by a test-only applier, on testdata and on natscli.** `internal/migrate` tests copy each testdata package set to a temporary module, answer all decisions with defaults, apply every step that carries machine edits in order (refusing a file whose hash differs from the step's recorded hash), and type-check after every step with `go/packages`. Guided sites carry no machine edits by design, so a component that still has guided sites keeps its legacy handle: its removal and rename steps are marked as waiting on those sites, and the applier stops before them. At the end, `legacyjs` must report exactly the legacy uses of the sites whose steps the applier did not apply — guided, unmapped and undecided sites, skipped components, and the roots and declarations of components whose removal waits — nothing more, which proves every applied edit compiles, and nothing less, which proves the classification is honest about what is left. Every other natsvet rule must report the same before and after. A second test, skipped unless `NATSVET_MIGRATE_CORPUS` points at the corpus cache, does the same on a copy of natscli (30 legacy uses, including a guided `Fetch` and a conditionally built `[]nats.JSOpt` that selects the constructor at runtime), or of another cached repository named by `NATSVET_MIGRATE_REPO`. go-choria and eventing-natss are planned by `scripts/migrate-corpus.sh`, which prints sites by class, components, blocked and skipped components and pending patterns; their components are reviewed by hand and the numbers recorded here. None of this joins CI until plans are stable enough to diff.

**A subscribe site owns its subscription's uses.** Replacing `sub, err := js.Subscribe(...)` changes `sub` from `*nats.Subscription` to `jetstream.ConsumeContext` (or `MessagesContext`), so the same site's edits rewrite the uses of that variable in its scope (`Unsubscribe` and `Drain` to `Stop` and `Drain`, `NextMsg` to `Next`) and the `*nats.Msg` reads in its handler; otherwise the step would not compile. A use the planner cannot rewrite exactly (the subscription stored in a field, passed to another function, or `NextMsg` with a timeout) makes the site guided.

## Risks / Trade-offs

- [The mapping table is large and hand-written; an entry can be wrong in a way that type-checks] → The three table tests catch missing and non-existent symbols and disagreement with `MIGRATION.md`; the applier catches text that does not compile, on testdata and on natscli; semantic mistakes (the `AddConsumer` case) are what the re-derivation task and review exist for, and every behavior fact is cited to a function.
- [A component spans a whole service] → The dual-handle order keeps each step small and compiling regardless of component size; the component is a unit of bookkeeping, not of commit.
- [Whole-module loads of large repositories (nats-server) are slow] → The plan command takes package patterns, so a team can plan one service at a time.
- [Handlers reached through function values the planner cannot resolve (stored in maps, returned from factories)] → Their `*nats.Msg` uses are not sites; the subscribe site notes that its handler is not statically known, and the loop's build step surfaces the type error when the handler type changes.
- [Byte offsets are brittle when a human edits between plan and apply] → The per-file hash makes staleness detectable; the skill says to re-plan after any manual edit, which is cheap.
- [The runtime stream lookup stays in migrated code] → It is exactly what legacy did, and the follow-up names the static candidate when one exists.
- [`MIGRATION.md` changes shape upstream and the agreement test breaks on parsing, not on content] → The parser reads only two-column tables whose cells contain backticked `nats.` and `jetstream.` identifiers; anything else is ignored; a parse that finds zero rows fails loudly rather than passing vacuously.

## Migration Plan

None for users of the analyzers: nothing they run changes. The subcommand is new. Modules that use it gain a committed `natsvet-migrate.json`.

## Resolved during implementation

Re-derived 2026-09-25 against nats.go v1.53.1 and nats-server v2.14.7; every fact in Context was confirmed at the function cited. The two open questions of the proposal stage are settled:

- **Listers.** Account-level legacy listers return bare channels and swallow errors (`jsm.go` `Streams`, `StreamsInfo`, `StreamNames`; `kv.go` `KeyValueStoreNames`, `KeyValueStores`; `object.go` `ObjectStoreNames`, `ObjectStores`). Their `jetstream` counterparts return listers whose channel accessor plus `Err()`/`Error()` carry the same data (`ListStreams(ctx).Info()`, `StreamNames(ctx).Name()`, `KeyValueStoreNames(ctx).Name()`, `KeyValueStores(ctx).Status()`, `ObjectStoreNames(ctx).Name()`, `ObjectStores(ctx).Status()`). Replacing the call expression with the accessor keeps the swallowed-error behavior, so these sites are mechanical, each with a follow-up to check the lister's error. Consumer listers (`ConsumerNames`, `Consumers`, `ConsumersInfo`) exist only on `jetstream.Stream` (`ConsumerNames`, `ListConsumers`), so they need a `js.Stream(ctx, name)` handle with its own error handling: guided.
- **Ordered consumers.** Legacy `nats.OrderedConsumer()` rejects durable, ack policy, max-deliver, deliver-subject and queue options (`js.go` subscribe); every option it accepts has a field in `jetstream.OrderedConsumerConfig` (`FilterSubjects` from the subject and `ConsumerFilterSubjects`, `DeliverPolicy` and its start options, `ReplayPolicy`, `HeadersOnly`, `InactiveThreshold`), and legacy's automatic heartbeats and flow control are handled inside the new pull-based ordered consumer. The new ordered consumer is pull-only and never acks, so an ordered subscription raises neither `subscribe-target` nor `ack`: the callback form is mechanical (`js.OrderedConsumer(ctx, stream, cfg)` then `Consume`, with the stream resolved as for any unbound subscription), the sync and channel forms are guided (`NextMsg(timeout)` and channel feeding depend on the surrounding code).

Found while implementing (2026-09-25), each with a testdata case:

- **Legacy's zero ack policy is none.** Legacy `AckNonePolicy` is 0 and `ConsumerConfig.AckPolicy` has no `omitempty` (`js.go`), so a `nats.ConsumerConfig{}` sends `"ack_policy":"none"`; jetstream's 0 is `AckExplicitPolicy` (`jetstream/consumer_config.go`). A renamed literal would switch consumers to explicit acks silently, so every converted legacy `ConsumerConfig` literal without an `AckPolicy` gets `AckPolicy: jetstream.AckNonePolicy`, and a zero legacy config declared without a literal is guided. Consumers created by subscribe calls need nothing: legacy subscribe sets `AckExplicitPolicy` when unset, which is jetstream's zero. Every other enum shares its zero value.
- **Push configs.** `AddConsumer`/`UpdateConsumer` with a config literal that sets `DeliverSubject` map to `CreatePushConsumer`/`UpdatePushConsumer`; `CreateConsumer` returns a pull consumer handle.
- **Constants and error values are not legacy symbols.** The generated legacy table holds types and functions only, so `nats.AckExplicitPolicy` and `nats.ErrKeyNotFound` are not `legacyjs` uses. They are sites anyway (not counted as legacy uses): a constant of a legacy type is renamed with the values it is used with; an error value the jetstream package declares under the same name is renamed with the call whose error it is compared against (`errors.Is`, `==`, a switch case), found as the last assignment of that error before the comparison; one without such a call is left alone. Legacy `AddConsumer` fails with `ErrConsumerNameAlreadyInUse` where `CreateConsumer` returns `ErrConsumerExists`, so that pair is renamed accordingly.
- **Units.** Sites that share a legacy-typed value (a config built in one statement and passed in another, an enum variable, a map of infos, values compared through `assert.Equal`) migrate in one step, found by a union-find over legacy-typed variables, results and struct fields; a use of such a value the planner cannot follow makes the unit guided. A struct field of a legacy type changes with its struct, an element with its container.
- **Placeholders.** A local legacy handle becomes unused once its last reader migrates, and a local sibling is unused until its first reader does; both are compile errors, so add-handle writes `_ = js` (and `_ = jsNew` when nothing reads the sibling yet) and remove-legacy deletes them.
- **Multi-call replacements stay expressions.** A call that needs a stream or consumer handle, and a subscribe call, becomes an immediately called function literal returning the legacy call's results, so the surrounding assignment and error handling are untouched.
- **Handlers.** A subscribe site takes over the sites inside its handler (a literal, or a function no core subscription uses) and embeds their edits; a handler shared with a core subscription is split into a `<name>JS` copy by default.
- **What cannot be threaded.** A handle returned from a function, received from a call the planner does not rewrite (a helper, a type assertion, a mock), or a parameter fed something other than a handle variable gets no sibling: its sites are guided and its component's removal waits on them. Methods of a type that implements a legacy interface (generated mocks) keep their signatures: retyping them breaks the implementation. Decided with the maintainer: this change threads variables, fields and parameters only, and the spec says so; threading through function results is left to `migrate-apply`, and would not have unlocked go-choria, whose helpers are interface methods with mock implementations (see the corpus numbers below).
- **Pending decisions.** When the sites of one pattern have different defaults (a bound subscription defaults to push), the most common default is asked at module scope and each other site at its own scope. `component` is always asked; until answered the steps assume `migrate`.

The machine share is low, and the reason is the same in all three: handles reach the code through things the dual-handle order does not thread. natscli builds `nc.JetStream(append(jsOpts(), ...)...)` with runtime options that pick the constructor, so every root is guided and every later step waits on it; the trial proves the plan honest, not that its edits compile. go-choria gets every KeyValue handle from `Framework.KV(...)`, an interface method with gomock implementations. eventing-natss (on v1.43.0, so its first step is `go get`) passes handles through test doubles. Per-site text is exact for the mechanical sites of all three; applying it needs the guided root or helper migrated first, which is the agent's work the skill describes.
