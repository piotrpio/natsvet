## Context

`headerkey` visits `CallExpr` (header methods) and `IndexExpr` (on `nats.Header`), resolves a constant key with `ConstString`, and looks it up case-insensitively in `natsapi.Header`, backed by `headers_table.go` — generated by `internal/tablegen` from the nats.go the `testdata` module pins, so it only knows headers that have a nats.go constant. The fix picks a constant from an imported package or falls back to the cased literal. See proposal.md for motivation and the corpus measurement.

Data this design rests on (2026-09-24, pinned corpus clones and nats-server v2.14.7 `8d8b69a`):

- nats-server v2.14.7's non-test Go files under `server/` contain 48 distinct `"Nats-…"` literals; two end in `-` and are prefixes (`Nats-Batch-`, `Nats-Expected-`), leaving 46 header names (`main` at `7cbac9c` adds `Nats-Stream-Identity`). nats.go and orbit.go add `Nats-Service-Error` and `Nats-Service-Error-Code` (micro), for 48 known headers.
- Within the known set only `Nats-Schedule`/`Nats-Scheduler` are within distance 2 of each other, and only `Nats-Scheduler` is a known header with letters appended to another. Both are known, so exact lookup settles them first.
- Every `"Nats-…"` literal in the nine corpus repositories that is not a known header: `Nats-UpTo-Sequnce` (natscli, distance 1), `Nats-TTLSeconds` (go-choria, distance 6 from its nearest, `Nats-TTL` + `Seconds`), `Nats-Has-More` (connect, distance 6), `Nats-X` (go-choria test, distance 3 from `Nats-TTL`, and not at a nats.go key site).
- The natscli site is `if k == "Nats-Subject" || … || k == "Nats-UpTo-Sequnce" { continue }` inside `for k, vs := range msg.Header`; the go-choria site is `msg.Header.Add("Nats-TTLSeconds", …)`.
- No ADR in nats-architecture-and-design reserves the `Nats-` prefix; connect ships its own `Nats-Has-More`.

## Goals / Non-Goals

**Goals:**
- Catch a key that is one slip away from a NATS header, with a rule the corpus shows is silent on legitimate `Nats-*` keys.
- One known set for both checks, derived from source rather than written by hand.
- See the key where the natscli bug actually is: a comparison in a range over the header.

**Non-Goals:**
- Guessing intent for keys far from every header. A distance-3 match on an 8-character header is as likely a different word as a typo.

## Decisions

**Two shapes instead of one threshold.** Edit distance ≤ 2 catches letter slips (`Sequnce`, `MsgId`); "known header + `[A-Za-z0-9]`" catches a unit or word glued onto a header (`TTLSeconds`), which no small distance reaches. The glued shape requires the next character to be a letter or digit, so `Nats-TTL-Seconds` — the way a custom header extends a namespace — is not reported. Alternative: the Levenshtein 2–3 threshold of `docs/design.md` §8 item 9 — rejected; distance 3 reaches `Nats-X` from `Nats-TTL` and still misses `Nats-TTLSeconds`. Alternative: report any unknown `Nats-*` key — rejected; connect's `Nats-Has-More` is legitimate and nothing reserves the prefix.

**`Nats-` prefix required for near-miss.** Without it, `Data-TTL` (distance 2 from `Nats-TTL`) and similar short user headers would be reported. With it, the check is confined to the namespace NATS uses, where a near-miss is overwhelmingly a mistake.

**Server header list as a generated Go table, checked in the corpus job.** `internal/tablegen` gains `ServerHeaders(dir)`: it parses every non-test `.go` file under `<dir>/server` with `go/parser` (no type checking, no module loading), collects string literals whose unquoted value matches `^Nats-[A-Za-z0-9-]+$` and does not end in `-`, and returns them sorted and unique (46 at v2.14.7, identical to a grep of the same tree). The generator writes `internal/natsapi/server_headers_table.go` (`var serverHeaders = []string{…}`) with the usual generated-code header. The command takes `-server <dir>`; the `go:generate` line passes `$NATS_SERVER_DIR`, and an empty value falls back to `$HOME/.cache/natsvet-corpus/nats-server`, the corpus clone. When neither exists, `make generate` regenerates the nats.go tables, leaves the committed server table untouched and prints that it skipped it, so a contributor without a server checkout is not blocked. A `-only server` selector writes just that table and skips the `testdata` load, so `scripts/corpus.sh` regenerates it from `$CORPUS_DIR/nats-server` into a temporary directory after the clone loop and `diff`s it against the committed file, failing with the diff; the corpus job needs no `testdata` download for it. Parsing rather than grepping means a header name quoted in a comment cannot contribute. Alternative: a committed text file embedded with `//go:embed` plus a shell script — equivalent in behavior, rejected with the maintainer so that every derived table is a `*_table.go` produced by `tablegen`. Alternative: type-based extraction through `tablegen`'s package loader — rejected; nats-server is not in the `testdata` module (adding it pulls the server's module graph into the test build), and many of its header names are inline literals or unexported. Alternative: a hand-written Go slice — rejected; it drifts silently when the pin moves, which is the failure the nats.go tables were built to prevent. The collection deliberately over-collects (internal headers such as `Nats-Server-Xkey`): a larger known set can only make near-miss quieter, and a case mismatch on any of them is still a real mismatch, since the server compares header names exactly.

**`natsapi.Header` keeps its signature; `KnownHeaders` is added.** The lazily built lowercase index now covers the nats.go table keys and `serverHeaders`; a server-only header returns its canonical name and no constants, which the existing fix code already turns into a cased literal. `KnownHeaders()` returns the sorted canonical names for the near-miss scan. The distance scan runs only for keys that start with `nats-` and miss the exact lookup — the uncommon case — over fewer than 50 short strings, with the row-minimum cutoff at 3, so cost is negligible.

**Key sites share one check.** The analyzer visits `CallExpr`, `IndexExpr`, `CompositeLit` (type `nats.Header` or `micro.Headers`, keys of `KeyValueExpr` elements), `BinaryExpr` (`==`, `!=`) and `SwitchStmt`, collects candidate key expressions, and runs one function: constant → exact known (nothing) → case-insensitive known (case diagnostic with fix) → near-miss (diagnostic without fix). For comparisons and switches, one operand (the tag) must be an identifier whose object is the `Key` of an enclosing `RangeStmt` with `Tok == DEFINE` whose `X` has type `nats.Header` or `micro.Headers`; the enclosing statement comes from the inspector stack. "The body never assigns `k`" is one `ast.Inspect` of the range body for an assignment, inc/dec or `&k` on that object. Alternative: `SingleDefinition` — rejected, it counts the range clause as an assignment by design. Alternative: any string variable compared to a `Nats-*` constant — rejected; outside a header range the variable can hold anything.

**Tie-breaking is deterministic, not clever.** The smallest distance wins, then lexical order; for the glued shape, the longest matching header wins (`Nats-Schedule-TTLx` names `Nats-Schedule-TTL`, not `Nats-Schedule`). When both shapes match, the distance shape reports. The message says "closest", which stays true under any tie rule.

**Messages.** Case diagnostics keep their wording. Near-miss: `header key "<key>" is not a header NATS sets or reads; the closest NATS header is "<Known>"`. The consequence (the server ignores the key on publish; a lookup or comparison never matches a NATS-set header) is the same at every site, so one sentence covers `Set`, `Get` and comparisons. No `SuggestedFix`: the project fixes only when the rewrite is certain, and `Nats-TTLSeconds` → `Nats-TTL` also changes the value's meaning (`30s` is a valid `Nats-TTL` value, but the intent has to be checked).

## Risks / Trade-offs

- [A legitimate custom header one or two edits from a NATS header (`Nats-Streams`)] → Not seen in the corpus; the diagnostic is still accurate about the key ("not a header NATS sets or reads"). If one shows up, the corpus triage records it and the threshold is revisited, per the project's "loose beats false warnings" rule.
- [A new server header used before the pin moves is reported as a near-miss of an old one] → Only if it is within the near-miss shapes of a known header; the corpus pin moves with each server release and the list check forces regeneration.
- [The case check now reports server-only headers] → Each report is a true mismatch; the fix is a cased literal, which is certain.
- [Header keys built by `http.CanonicalHeaderKey` or `textproto` elsewhere] → Non-constant, never examined.

## Migration Plan

None. New diagnostics appear on upgrade; existing ones and their fixes are unchanged. The `headerkey` Doc string and the `rule-headerkey` purpose paragraph are rewritten to cover near-misses and nats-server headers (the purpose paragraph in the main spec at archive time, since the delta format carries requirements only).
