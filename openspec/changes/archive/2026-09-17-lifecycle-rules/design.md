## Context

Ten default-on rules and one opt-in rule exist; `natsapi` has callee matching, constant extraction, `CompositeFields`, `SingleDefinition`, `EnclosingFuncBody` and the `Masker`. See proposal.md for motivation. The three rules here are statement-shape rules: each keys on where a call's result goes (`handle`, `pubasync`) or on the statements around a call inside a loop (`msgloop`), and one of them (`pubasync`) is the first to reason about the whole package. Behavior was re-verified against nats.go v1.53.1 (the `testdata` pin) this session, and every check list below is re-derived from that source at implementation time, not copied from `docs/design.md` §3.2:

- `jetstream.Consumer.Consume`/`Messages` and the new `jetstream.PushConsumer.Consume` (absent from `docs/design.md`) return the only `Stop`/`Drain` for the pull or push subscription they start. `jetstream.StopAfter` is a named `int` type, not a function; with it, `Consume` and `Messages` stop themselves (`consumeOpts.StopAfter`).
- `jetstream.KeyValue.Watch`/`WatchAll`/`WatchFiltered` build a legacy push subscription with `nats.OrderedConsumer()` (`kv.go` `WatchFiltered`); the `ctx` argument only scopes the subscribe request (`nats.Context(ctx)`), so the watcher lives until `Stop` (`w.sub.Unsubscribe()`) or the connection closes. `ObjectStore.Watch` and the legacy `nats.KeyValue`/`nats.ObjectStore` watchers are the same shape. `KeyLister` from `ListKeys` terminates on its own and is not a handle.
- `pullSubscription.Next` (`pull.go`) returns `ErrMsgIteratorClosed` immediately when `closed && !drainMode`, so a `continue`-on-error loop never exits (and spins, unless the branch sleeps). `Consumer.Next` is a one-message `Fetch` with a timeout and cannot spin.
- `fetchResult.err` is set for every terminal status except timeout, no-messages and max-bytes, for `ErrNoHeartbeat` via `sub.errs`, and for the context's error; `Messages()` is simply closed. Legacy `Subscription.FetchBatch` returns `nats.MessageBatch` with the same two methods.
- `handleAsyncReply` (`jetstream/publish.go`, and `js.go` for the legacy API) delivers an async publish error to `paf.errCh` and to `asyncPublisherOpts.aecb` (`WithPublishAsyncErrHandler` / `nats.PublishAsyncErrHandler`) and nowhere else; a successful ack goes to `paf.doneCh` and to `asyncPublisherOpts.ackcb` (`WithPublishAsyncAckHandler`, `jetstream` only — the legacy API has no ack handler) and nowhere else. The two callbacks are disjoint: an ack handler never sees an error. `PublishAsyncComplete` closes when the pending map is empty regardless of outcome. nats.go's own `ObjectStore.Put` installs the error handler in one place and awaits completion in another, and discards every future in between.
- `Conn.Drain` (`nats.go`) is `go nc.drainConnection(); return nil`; `drainConnection` unsubscribes, flushes and closes in that goroutine. Process exit kills it. The existing `drain` analyzer already has `exempt` (main/test detection) and `checkDeferred` (the trailing-`Drain` walk) to build on.

A grep over the local corpus cache (the same pinned clones the gate uses) gives the baseline the proposal quotes: 28 discarded handles (27 in tests that assert an error from the call, one in `examples/jetstream/js-ordered-consume/main.go`), 54 discarded futures (all but ~8 within reach of a `PublishAsyncComplete`), no `Next` spin loop, 58 `range x.Messages()` sites of which roughly 35 have no `Error()` call in the file, including `examples/docs/jetstream-basic/main.go`; no `defer nc.Drain()` in any `main` (the 76 deferred `Drain`s are `Subscription.Drain` in nats-server tests) but two `nc.Drain()` followed by `log.Fatalf` in nats.go's `examples/nats-qsub` and `nats-rply`; about 480 discarded `*nats.Subscription`s, 50 in production code, all lifetime-of-connection; and 57 discarded `Fetch` batches, all in tests.

Corpus outcome (2026-09-17, after implementation): 14 new lines, 6 `TP` and 8 `FP`, no false positive on non-test code, so `handle` and `pubasync` stay default-on. Per rule: `handle` 11 (3 `TP` — the `js-ordered-consume` example, natscli's `events` command with a bare `cons.Consume(...)`, natscli's bench service; 8 `FP`, every one a test asserting an error from `Watch`/`WatchAll` before any watcher exists); `msgloop` 1 (`TP`, the `jetstream-basic` docs example; the nats-server batch site is behind a positive `include_js_long_tests` build tag and is not compiled); `pubasync` 0 (every corpus package that discards a future also awaits `PublishAsyncComplete` or installs an error handler — the rule's precision rests on its seven testdata packages, not on the corpus); `drain` 2 (`TP`, `nats-qsub` and `nats-rply`). The grep baseline overcounted because the corpus lints nats.go's `./examples/... ./test/...`, not `jetstream/test/`, which is where the discarded `Consume` calls and unchecked batches of the grep live.

## Goals / Non-Goals

**Goals:**
- Three rules with the same posture as Tier 1: a statement shape decides, never a guess about control flow elsewhere; when the rule cannot see the whole story (a handle stored in a field, a batch passed to a helper) it stays silent.
- Reuse of the inspector stack and `SingleDefinition` so no rule needs its own dataflow.
- The corpus numbers, not this document, settle the two open defaults.
- Close `docs/design.md` §8 item 2 by shipping the `Drain`-in-`main` check default-on: draining and then exiting drains nothing, and docs snippets that show it are corrected upstream rather than accommodated here.

**Non-Goals:**
- Escape analysis: a handle kept in a variable and never stopped is not reported, however obvious.
- Any change to the corpus mechanism, and no new flags: every check here is default-on or absent.

## Decisions

**Discard shapes are one helper.** `handle` and `pubasync` both ask the same question of a `CallExpr`: is its first result thrown away? `natsapi.Discarded(stack []ast.Node) bool` answers from the inspector stack: the parent is an `ExprStmt`, or an `AssignStmt` (any position — a plain statement or the `Init` of `if`/`for`/`switch`) whose single right-hand side is the call and whose first left-hand side is the blank identifier, or a `ValueSpec` `var _ = call`. `go`/`defer` statements are not discards for this purpose: `go cons.Consume(h)` is nonsense nobody writes and `defer` never applies to these calls. Alternative: a per-rule walk of `AssignStmt`s looking for hook calls on the right — rejected; the inspector already visits every call once, and the stack tells the story.

**`handle` hooks are a table** `{pkg, recv, method, kind}` as in `syncsub`, plus one function hook (`micro.AddService`). Kinds carry the type name and the message tail: `consume`/`messages` → "the consumer can never be stopped or drained"; `keywatcher`/`objwatcher` → "the watcher can never be stopped and its subscription lives as long as the connection"; `service` → "the service can never be stopped and keeps answering until the connection closes". `IsMethod` matches interface methods by declaring interface, so `jetstream.Consumer.Consume` and `jetstream.PushConsumer.Consume` are two rows and an ordered consumer (also a `Consumer`) needs none. `*nats.Subscription` constructors are not in the table: the corpus shows about 480 discards, 50 of them in production code and every one a subscription meant to live as long as the connection, so neither a default-on row nor a `-handle.subscriptions` flag (the design doc's parking spot) has evidence behind it; the numbers go to `docs/design.md` §8. The `StopAfter` exemption is `natsapi.IsNamedType(info.TypeOf(arg), JetStream, "StopAfter")` over the call's arguments: a conversion `jetstream.StopAfter(10)` and a variable of that type both have the named type, so no AST pattern is needed.

**`msgloop` never-exits detection is a statement-list match, not a call match.** Walk `ForStmt`s with nil `Init`, `Cond` and `Post` (a conditional loop runs only until its condition flips; the message promises "never exits" and must be true). In the body's statement list find, at index `i`, an `AssignStmt` with two left-hand sides and one right-hand `CallExpr` whose callee is `IsMethod(JetStream, "MessagesContext", "Next")`, followed at `i+1` by an `IfStmt`; or an `IfStmt` whose `Init` is that assignment. The condition must be `BinaryExpr{!=}` between `nil` and an identifier resolving (`info.ObjectOf`, defined by `:=` or used by `=`) to the assignment's second left-hand object. The then-branch disqualifies itself if `ast.Inspect` finds a `ReturnStmt`, a `BranchStmt` with `BREAK` or `GOTO`, a `CONTINUE` with a label other than the loop's own, a call to builtin `panic` or `IsFunc("os", "Exit")`, or a call whose callee name starts with `Fatal` (`log.Fatal*`, `t.Fatal*`); it qualifies if its last statement is an unlabeled or self-labeled `continue`, or if `Else != nil`. Finally `ast.Inspect` over the whole loop body for any identifier whose object is `ErrMsgIteratorClosed` in `JetStream` disarms the report: the author knows the iterator can close, wherever they check it. A `time.Sleep` in the branch does not disqualify it: the loop then leaks a goroutine that logs `ErrMsgIteratorClosed` once a second instead of burning CPU, the fix is the same, and the message says "never exits" rather than "spins" so it stays true. Alternative: report any `continue` on a `Next` error anywhere in any loop — rejected; `for ctx.Err() == nil` and bounded loops have an exit the author chose, and second-guessing it is a false positive.

**`msgloop` batch detection rides on `SingleDefinition`.** On each `RangeStmt` whose `X` is `<r>.Messages()` with callee `IsMethod(JetStream|Core, "MessageBatch", "Messages")` and `<r>` a bare identifier, `SingleDefinition(r)` must be a call whose callee is one of `Consumer.Fetch`/`FetchBytes`/`FetchNoWait` (JetStream) or `Subscription.FetchBatch` (Core); the method name goes into the message. Then one `ast.Inspect` over the enclosing body collects every `Ident` whose `info.Uses` is `<r>`'s object: each must be the `X` of a `SelectorExpr` named `Messages` or `Error` that is the `Fun` of a `CallExpr`, otherwise the batch escaped (passed on, stored, compared) and the rule stays silent; if any is `Error`, the rule stays silent. Closures are inside the body and are seen. A parameter has no single definition and is skipped by construction. Alternative: type-driven (`<r>` has type `MessageBatch`) without the definition — rejected; a parameter's `Error()` is the caller's business.

**`pubasync` exemptions are package-wide.** Both signals that the author handles async errors — a handler on the `JetStream` instance, a completion wait at the end of a batch — live naturally in other functions of the same package (a constructor, a `Close`), and nats.go's own `ObjectStore.Put` is the reference example of the split. The rule computes `natsapi.PackageUses(info, JetStream, "", "WithPublishAsyncErrHandler") || PackageUses(info, Core, "", "PublishAsyncErrHandler") || PackageUses(info, JetStream, "Publisher", "PublishAsyncComplete") || PackageUses(info, Core, "JetStream", "PublishAsyncComplete")` once at the top of `Run` and returns early when true; only then does it walk calls to `PublishAsync`/`PublishMsgAsync` and report those that are `Discarded`. `IsMethod` matches by declaring interface: in `jetstream` that is `Publisher`, which `JetStream` embeds (found at implementation time — the proposal said `JetStream`); in the legacy package it is `JetStream`, which `JetStreamContext` embeds. `PackageUses` iterates `info.Uses` — the objects every identifier in `pass.Files` resolves to, which is exactly the package (plus its test files when the driver analyzes the test variant) and never a dependency — and matches with `IsFunc`/`IsMethod`. Alternative: the function-wide scope of `docs/design.md` §3.2 — rejected as the default because the `Publisher.publish`/`Publisher.Close` split is idiomatic and would be a false positive on production code, the one kind of finding a default-on rule may not produce; the wider scope's cost is a miss when the handler lives in another package, which the function-wide scope missed too.

**`WithPublishAsyncAckHandler` is not an exemption.** It is the callback-style replacement for the future's `Ok()` and the natural reason to discard futures, but `handleAsyncReply` invokes it only after a valid `PubAck`; errors still go only to `errCh` and `aecb`. A package that installs the ack handler and not the error handler has wired up half of the callback style and loses every failure — the finding the rule exists for, and the message ("never sets an async error handler") says what is missing. Paired with the error handler it is silent through the existing exemption. Alternative: treat it as lifecycle evidence like `PublishAsyncComplete` — rejected (decided with the maintainer); it would silence exactly the half-wired case.

**`drain` in `main` reuses the existing walk.** Inside `run`, for a `FuncDecl` that `exempt` classifies as `main` in `package main` (not the test cases — a test's return does not exit the process, so its deferred `Drain` proceeds), a third pass over the body: `defer <x>.Drain()` statements report directly; a `<x>.Drain()` expression statement reports when it is the last statement of the body, is followed by a `ReturnStmt`, or is followed by an `ExprStmt` whose call is `IsFunc("os", "Exit")` or has a callee name starting with `Fatal` — the same terminator test `msgloop` uses, promoted as `natsapi.ExitsProcess` because the two rules live in different packages (builtin `panic`, `os.Exit`, a declared `Fatal*` function or method; a func value is not examined whatever its name). The deferred-`Close` pass keeps its `main` exemption so the trailing `Drain` in `main` gets one diagnostic, the process-exit one. `Subscription.Drain` is not hooked: the rule's hook set is `Conn`, and the corpus has no `Subscription.Drain` in a `main`. Alternative: `-drain.main` off by default, as `docs/design.md` §3.2 suggested — rejected; a flag nobody turns on is the same as not shipping (see the subscriptions decision), and the maintainer decided the docs, not the rule, should change.

**Helpers new vs reused.** New in `natsapi`, each with a table test: `Discarded` (two rules), `PackageUses` (one rule today, but the first package-scope question and the mechanism `docs/design.md` §8 item 5 wants for `headerkey`), `IsNamedType` (a general `go/types` question next to `IsMethod`), `ExitsProcess` (two rules). Reused: `Callee`, `IsMethod`, `IsFunc`, `IsPkg`, `SingleDefinition`, `EnclosingFuncBody`. Not promoted: the `msgloop` statement-list matcher, the hook tables. Not used: the `Masker` — `docs/design.md` §6 item 5 is corrected to drop it.

**Testdata.** `testdata/handle/{jetstream,legacy,micro}.go`, with a same-named user type in `jetstream.go` for the negative case and an unannotated `nc.Subscribe` discard in `legacy.go`. `testdata/drain/cmd/main.go` grows the process-exit shapes (its existing `defer nc.Close(); nc.Drain()` main flips from unannotated to a `// want`), and `testdata/drain/drain_test.go` gets a `defer nc.Drain()` negative. `testdata/msgloop/{iterator,batch,legacy}.go`. `pubasync` needs one package per exemption state: `testdata/pubasync/` (no error path, reports), `testdata/pubasync/handler/`, `testdata/pubasync/complete/` (the signal in a different function of the package), `testdata/pubasync/ackhandler/` (ack handler only — reports), `testdata/pubasync/bothhandlers/`, `testdata/pubasync/legacy/` and `testdata/pubasync/legacyhandler/`; the analyzer test runs the pattern `natsvet/testdata/pubasync/...`.

**Defaults are decided by the corpus task, with a stated rule.** All three register in `Analyzers()`. After triage, `handle` or `pubasync` moves to `OptIn()` (gaining the `enable` flag) only if the corpus shows a false positive on non-test code, where a false positive is a site at which the message is *untrue* — a handle that is stopped through a path the rule cannot see, a future whose error is observed some other way — and not a site where the author evidently meant the discard but the message still holds; that is a true positive they may choose to ignore. A `_test.go` file that discards a handle to assert an error, or ranges a batch to count messages, is accepted noise and tagged `FP` with that reason, as the config rules' test findings are, and never demotes. The outcome and per-rule counts are recorded in this file's Context and in `docs/design.md` §8 item 3.

**`docs/design.md` updates.** §3.2: `PushConsumer.Consume`, the `StopAfter` exemption, the `handle` subscriptions flag removed with the corpus numbers, the condition-less loop, `else` and backoff shapes for `msgloop`, the package-wide `pubasync` exemptions and the ack handler's non-exemption with the reason, and the `drain` extension rewritten as shipped (default-on, `main` only, the exit shapes). §6: item 5 done, Masker dropped. §8: items 2 and 3 answered; new items for the discarded `Fetch` batch (57 test sites, 0 production), for `Subscription` discards (480/50) and for `go`/`defer` discards should they ever appear.

## Risks / Trade-offs

- [`handle` on `_, err = cons.Consume(...)` in a `main` that exits on a signal] → reported by design; the sibling nats.go examples keep the context and `defer cc.Stop()`, and a graceful shutdown wants `Drain()`. If dogfooding shows the pattern dominates real `main`s, the demotion rule above applies and the message stays as a nudge.
- [`pubasync` silenced by an unrelated `PublishAsyncComplete` in a test file of the same package] → accepted; a false negative on one package is cheaper than a false positive on the idiomatic split, and the message makes the reasoning explicit ("this package never...").
- [`msgloop` never-exits check fires on a loop with a `select` on `ctx.Done()` elsewhere in its body] → intended: after `Stop`, that loop still runs until the context is canceled, and the check only fires when nothing in the loop names `ErrMsgIteratorClosed`; the fix is the same one-line `errors.Is`.
- [`msgloop` batch check fires on tests that count messages] → about 35 lines of `FP` triage in nats.go's tests, each with the same reason; the docs example without `Error()` is the true positive that justifies the noise.
- [Analyzing the test variant of a package changes `PackageUses`] → the driver runs the rule on `pkg` and on `pkg [pkg.test]` separately; the non-test variant sees only non-test files, so a handler installed in a test cannot hide a production discard from `natsvet ./...` — only from the test-variant pass, and the checker prints a diagnostic reported by both passes once (`checker/print.go` keys on position and message).
- [`drain`'s process-exit check contradicts public docs snippets that show `defer nc.Drain()` in `main`] → intended; the maintainer's position is that the snippets are wrong and will be corrected, and the message tells the reader what to do instead. If a docs-derived complaint arrives before the docs change, the rule is one flag to disable and the argument is the one worth having.
- [`IsNamedType` on `StopAfter` misses an untyped constant argument] → impossible: `Consume`'s variadic parameter is an interface, so a bare `10` does not compile; every accepted argument has the named type.
