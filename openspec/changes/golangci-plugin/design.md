## Context

Fourteen rules are registered through `natsvet.Analyzers()` / `OptIn()`; opt-in rules carry a boolean `enable` flag on their `analysis.Analyzer`; `cmd/natsvet` is `multichecker.Main(natsvet.All()...)` behind a `-version` pre-check. See proposal.md for motivation. The golangci-lint contract was verified this session against `github.com/golangci/plugin-module-register` (`register/register.go`) and golangci-lint `main` (`pkg/lint/lintersdb/builder_plugin_module.go`, `pkg/goanalysis/runners.go`, `pkg/config/linters_settings.go`):

- A plugin is a package that calls `register.Plugin(name, New)` in `init()`; `New(settings any) (register.LinterPlugin, error)`; `LinterPlugin` is `BuildAnalyzers() ([]*analysis.Analyzer, error)` and `GetLoadMode() string` with `register.LoadModeSyntax = "syntax"` / `register.LoadModeTypesInfo = "typesinfo"`.
- `register.DecodeSettings[T](raw)` round-trips the YAML-decoded value through JSON with `DisallowUnknownFields`; a `nil` settings value decodes to the zero `T` without error.
- golangci-lint looks the plugin up by the config key under `linters.settings.custom` (`register.GetPlugin(name)`), fails with `plugin(<name>): ...` when nothing is registered under it, names the linter after that key, and applies `WithLoadForGoAnalysis` for type-info mode. `CustomLinterSettings` has `type`, `path` (Go-plugin only), `description`, `original-url`, `settings`.
- `buildIssues` sets the issue text to `<analyzer name>: <message>` whenever the analyzer name differs from the linter name — with fourteen analyzers under one linter, every finding carries its rule id.
- `plugin-module-register`'s `go.mod` requires only `golang.org/x/tools v0.32.0`; ours is v0.49.0. Latest golangci-lint is v2.13.2 (2026-08-27).
- `go list ./...` inside the `testdata` module resolves its 26 packages; the module already carries every rule's positive and negative cases, which makes it the parity corpus.

## Goals / Non-Goals

**Goals:**
- A golangci-lint binary with natsvet in it, buildable from a checkout today and from a version once one exists, with the rule set and defaults identical to the standalone binary.
- Parity proven by running both over the same code, not by inspection.

**Non-Goals:**
- Any change to rule behavior, messages or the registry.
- The upstream PR; only its checklist (below) so nothing is rediscovered later.

## Decisions

**Package `plugin` in the main module.** `github.com/piotrpio/natsvet/plugin`, package `plugin`, one file: `init()` registers `natsvet`; `New` decodes settings and returns a value holding the analyzer list; `BuildAnalyzers` returns it; `GetLoadMode` returns `register.LoadModeTypesInfo`. `.custom-gcl.yml` names `module: github.com/piotrpio/natsvet` with `import: github.com/piotrpio/natsvet/plugin`, since golangci-lint imports the module root by default and the root package must stay free of the register dependency for `cmd/natsvet`. Alternative: register from the root package — rejected, it would link `plugin-module-register` into the standalone binary for nothing. Alternative: nested module — rejected with the maintainer (proposal Non-goals): a second tag and a pseudo-version bump per rule change, because `replace` directives in a plugin's `go.mod` are ignored when golangci-lint assembles the custom binary's module.

**Settings are two lists, validated strictly.** `type settings struct { Enable []string \`json:"enable"\`; Disable []string \`json:"disable"\` }` through `register.DecodeSettings`, so an unknown key fails with golangci-lint's own decode error. `New` then builds a name index over `natsvet.All()` and rejects any name not in it with `natsvet: unknown rule %q in %s`. Redundant entries (a default-on rule in `enable`, an opt-in rule in `disable`) are accepted: they change nothing and rejecting them would make configs brittle across a rule's promotion or demotion. The returned list is `Analyzers()` minus `disable` followed by the `OptIn()` rules named in `enable`. Alternative: expose every analyzer flag as a `map[string]map[string]string` — rejected, no rule has a flag other than `enable` and the design keeps it that way (§2.3).

**Opt-in flags are set explicitly on every build.** For each opt-in analyzer, `a.Flags.Set("enable", "true")` when listed, `"false"` otherwise. Analyzers are package-level values, so setting only the listed ones would let an earlier construction leak into a later one (the unit tests construct the plugin repeatedly; golangci-lint constructs it once). Clearing the others makes `New` deterministic for the same settings. The flag stays the mechanism rather than a second switch because it is what the spec (analyzer-framework: opt-in rules) defines and what `multichecker` and `unitchecker` honor.

**Type-info load mode.** Every rule uses `pass.TypesInfo`; syntax mode would hand them nil type information and silence all of them. Not configurable.

**Two `.custom-gcl.yml` shapes, one file.** The repository root carries the checkout form (`version: v2.13.2`, `name: custom-gcl`, `destination: ./bin`, plugin with `path: .`), which is what CI and a developer use; `bin/` is already ignored. The README shows the user form with `version:` instead of `path:` and says a tag, or `main` until there is one — `golangci-lint custom` resolves versions the way `go get` does, so a branch name yields a pseudo-version. Alternative: a second file under `scripts/` for CI — rejected; `golangci-lint custom` reads only `.custom-gcl.yml` in the working directory.

**Parity script.** `scripts/plugin.sh <natsvet binary>`: (1) requires a `golangci-lint` on `PATH` (any v2; it only orchestrates the build) and runs `golangci-lint custom` at the root; (2) checks that `bin/custom-gcl version` reports the version pinned in `.custom-gcl.yml`, so the pin is what is verified — found at implementation time: the installed golangci-lint need not match the pin (a Homebrew v2.10.1 built the v2.13.2 binary in twelve seconds), so requiring equality would only get in a developer's way; (3) runs `bin/custom-gcl run ./...` in `testdata` with `testdata/.golangci.yml`, accepting exit codes 0 and 1 (issues found) and failing on any other; (4) runs `<natsvet> -<rule>.enable ... ./...` in `testdata` for every `.enable` flag the binary exposes (the `optin_flags` walk from `corpus.sh`), accepting its diagnostics exit code the way `corpus.sh` does; (5) normalizes: golangci-lint lines lose the `<rule>: ` after the position (`sed -E 's/^([^:]+:[0-9]+:[0-9]+: )[a-z]+: /\1/'`), natsvet lines lose the absolute `testdata/` prefix; both sorted; `diff` decides. The `testdata/.golangci.yml` is `version: "2"`, `linters.default: none`, `linters.enable: [natsvet]`, `custom.natsvet` with `type: module` and `settings.enable` listing every opt-in rule, `issues.max-issues-per-linter: 0`, `issues.max-same-issues: 0`, `issues.uniq-by-line: false` (testdata lines can carry two findings), `output.formats.text` to stdout with `print-linter-name: false` and `print-issued-lines: false`, `output.show-stats: false`, and `run.relative-path-mode: cfg` so paths are relative to the module. The exact v2 keys are confirmed at implementation time with `bin/custom-gcl config verify`, which validates the file against golangci-lint's schema. An opt-in rule missing from the YAML's `enable` shows up as natsvet-only lines in the diff, so the list needs no separate guard.

**CI job `plugin`.** `actions/setup-go` at 1.26, `golangci/golangci-lint-action` with `install-only: true` and the pinned version (a downloaded binary; `go install` of golangci-lint would build it from source every run), then `make plugin`, where `plugin: build` runs the script with `bin/natsvet`. Separate job, as `corpus` is, so its failure is reported on its own; the workflow installs the pinned version too, for the download cache's sake; the script verifies the pin on the built binary either way.

**Plugin unit tests.** `plugin/plugin_test.go`: `register.GetPlugin("natsvet")` returns the constructor (registration); a table over settings values as golangci-lint delivers them (`nil`, `map[string]any{"enable": []any{"legacyjs"}}`, `disable`, both, unknown name, unknown key, redundant names) checked against the returned analyzer names and the `enable` flag value of each opt-in analyzer; `GetLoadMode` equals `register.LoadModeTypesInfo`. Table-driven, no golangci-lint process involved; the parity script is the integration test.

**Docs.** README gains a "golangci-lint" subsection under Use: the user `.custom-gcl.yml`, `golangci-lint custom`, the `.golangci.yml` block (`type: module`, `description`, `original-url`, `settings.enable`/`disable`), a sample finding line showing the `<rule>:` prefix, and the note that `//nolint:natsvet` covers the whole linter. `docs/design.md`: §2.1 names `plugin-module-register` as the second production dependency and why it is acceptable (golangci-owned, depends only on x/tools, not linked into `cmd/natsvet`); §5 item 4 records the plugin as shipped and the upstream PR as waiting on the move; §6 item 6 done.

**Upstream PR checklist (for the change after the move).** Final module path and the §8 item 4 name decision (`natsvet` vs `natslint`/`natscheck`); in golangci-lint: `pkg/golinters/<name>/<name>.go` wrapping `natsvet.All()` with the settings struct mapped from `pkg/config/linters_settings.go`, a `linterdb` entry with `WithSince`, `WithLoadForGoAnalysis` and `WithURL`, the `.golangci.reference.yml` and JSON-schema entries, `docs/src/docs/usage/linters.mdx` generation, and the new-linter checklist from golangci-lint's contribution guide (stable API, tests, no `replace`, a release tag). Everything but the path and name exists after this change.

## Risks / Trade-offs

- [golangci-lint excludes paths containing `testdata` by default] → `run.relative-path-mode: cfg` makes paths relative to the `testdata` module root, so no path contains the component; if a version still drops them the parity diff is empty on one side and fails loudly, and `linters.exclusions.paths-except` is the fix. Checked in the first run.
- [`golangci-lint custom` builds golangci-lint from source, needs the network and a minute or two] → CI only; cached by the Go build cache across runs; the sandboxed shell cannot run it (module proxy), so the parity script runs unsandboxed locally, like `make corpus`.
- [Version skew between `.custom-gcl.yml` and the CI action] → harmless: the action's binary only orchestrates `custom`, and the script verifies the built binary reports the pin. Bumping the pin is one edit; the workflow's `version` is updated alongside so the download cache stays useful.
- [Flag mutation on package-level analyzers] → `New` sets every opt-in flag explicitly; documented on the function. Nothing else in the process constructs the plugin.
- [The pre-tag `version: main` form embeds a pseudo-version that stops matching the README once rules are added] → expected; the README says so, and a tag makes the form stable.
